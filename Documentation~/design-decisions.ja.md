# 設計上の決定事項

AddressTeller の挙動には、一見不便に見えても意図的に選んでいる仕様がいくつかある。
ここでは、その判断とその理由をまとめる。仕様変更を検討する際は、まずここに書かれた前提が変わったかどうかを確認してほしい。

## アドレスの優先順位と競合

`Order` は評価順序であると同時にアドレスの優先順位でもある。アドレスを発行するルール（`Address()` を呼んだルール）が2件以上マッチした場合、`Order` が最小のものが採用されそのアドレスが書き込まれる——これが、広いルールを特定のルールで上書きするための標準的な書き方（[ルールの書き方](writing-rules.ja.md#評価ルールと挙動)に例がある）。競合エラーになるのは、*Order が最小*のマッチが2件以上で同点だった場合のみ。Apply・Validate で同じ判定をする。

同点のルールのどちらかを暗黙に採用すると、同じ優先順位を宣言した2つのルールのどちらが選ばれるかを決める根拠が定義側に何も無いまま最終アドレスが決まってしまう。曖昧な状態は黙って解決せず、エラーとして表面化させる方を選んだ。

ここまでの節は、すべて*1アセット内*の競合——1つのアセットに複数ルールがそれぞれ異なるアドレスを返した場合——についての話である。別々のアセットが同じアドレス文字列になってしまうケースはここでは扱っていない。各アセットは独立に評価されるため、上記の競合判定ではそもそも検出できない別の問題である。`Validate` / `Apply All`（したがって `CheckCLI` / `ApplyAllCLI` / `ApplyWithValidateCLI` も）は、予測される最終状態全体を追加でスキャンし、アセット間のアドレス重複を `ValidationStatus.DuplicateAddress` として報告する。これは報告専用であり書き込みを止めることはない——Addressables 標準の Groups ウィンドウ自体、重複したアドレスの登録を受け付けるため。ただし重大度は、AddressTeller 自身がその重複に対して手を打てるかどうかで変わる。重複している当事者のうち1件でもこのランで AddressTeller 自身がアドレスを書く対象であればエラー（ルールを直せば直せる問題）とし、どちらの資産もこのランのアドレス書き込み対象に含まれない場合（例えば、どちらのルールも触れない既存エントリ同士）は、ブロックしない通知として扱う。

## ラベルは全ルールから蓄積する

ラベルはアドレスと異なり、マッチした全ルールから蓄積する（複数ラベルの同時付与）。ラベルは1アセットに複数付くことが正常な使い方であり、競合の概念がない。分類軸ごとに独立したルールを書けるようにするため、蓄積を既定とする。

## 存在しないグループは作らない（既定）

既定では、ルールが指定したグループが存在しない場合はエラーにし、自動生成はしない。グループはバンドル設定（圧縮・分割方針）を伴う設計上の単位であり、タイプミスで意図しないグループが量産されると気づきにくい。グループの作成は明示的な操作に委ねる。自動作成が必要な場合に備え、既定OFFのオプトイン設定を別途用意している——`Project Settings > AddressTeller` の**存在しないグループを自動作成する**（`AutoCreateMissingGroups`）。詳細は[Project Settings](operations.ja.md#project-settings)を参照。

## 削除は資産単位の所有権で判定する

AddressTeller が所有するのは、あなたのルールがアドレスを宣言したグループだけである——あるグループは、いずれかのルールが `Group("X")` を呼び、さらにそこで `Address(...)` を呼んだ時点で初めて所有下になる。所有するグループの中では、ルールに一致するようエントリを作成・移動・削除する。所有していないグループに新しくエントリが作られることはなく、後述するクリーンアップがそこからエントリを削除・移動することもない——ただし「所有していない」は「一切触れない」という意味ではない。ラベルのみルール（`AnyGroup()`、または `Address()` をまだ呼んでいない `Group()` ルール）は、そこにある既存エントリにラベルを加えることがある（ラベルの書き込みは加算的であり所有権を問わない。上記「[ラベルは全ルールから蓄積する](#ラベルは全ルールから蓄積する)」参照）。また、アドレスルールにマッチした資産は、それが現在どのグループに属していても（AddressTeller が所有していないグループであっても）そのルールのグループへ移動される。

`CleanupStaleEntries`（既定: OFF）はこの所有権を使って `Apply All` が削除してよい範囲を決める。判定は資産（GUID）単位で行う: 所有グループ内のエントリは、そのエントリが対応する資産に現在どのルールもマッチしなくなった時点で削除される。ここでの「マッチしなくなった」とは、その資産に対してアドレスもラベルも一切生成しない（真に無マッチである）ことを指す。ラベルのみルール（`AnyGroup()` や `Address()` を呼ばない `Group()` ルール）がまだマッチしている場合は「マッチする資産」として扱われ、削除対象にはならない。この規則の帰結として、手動で登録したエントリであっても、それが所有グループ内にあり、かつどのルールにもマッチしなくなれば削除される——AddressTeller に触れさせたくないエントリを置きたい場合は、所有していない別グループに登録すること。

**この設定、および `PostprocessEnabled`（インポート時自動適用）が既定 OFF である理由**: AddressTeller を安全に導入するなら、実際には「まず手動で `Apply All` を実行し、何が変わるかを確認してから、削除や無人実行を許可する」という手順になる。多くの導入者がすぐにオフへ戻すことになる既定値を出荷するより、この安全な出発点そのものを既定にした——書き込みは `Apply All`（または `Apply with Validate`、CLI のいずれか）を明示的に実行したときにだけ発生し、削除は一切起きない。自動化（インポートだけで書き込みが走ること、無マッチエントリが自動で消えること）は、手動の `Apply All` の結果を見て納得し、より多くをツールへ委ねる準備ができてから opt-in するものという位置付けである。有効にする順序の推奨は [クイックスタート](../README.ja.md#クイックスタート) を参照。`CleanupStaleEntries` が OFF の間は、削除されるはずだったエントリが書き込みを止めない通知 `ValidationStatus.UnmatchedEntryKept` として報告されるため、ON にする前に効果を確認できる。

削除はエントリ単位（`RemoveAssetEntry`）で行うため、そのエントリが持っていたアドレスとラベルはまとめて失われる。「エントリは消すがラベルだけ剥がさずに残す」という個別の処理はない。意図的に避けているのは、マッチが継続しているエントリからラベルを剥がすことである。ラベルは「全ルールから蓄積する」という設計上、どのルールがいつ付与したラベルかを後から一意に特定できないため、`Apply All` は生存しているエントリに対してラベルを加算するだけで、自ルール以外が付与したラベルを剥がすことはない。削除してよいと確信できる範囲（所有グループのエントリ）だけを自動操作の対象にし、判断が難しい操作（事後的なラベル剥がし）は利用者の手動操作（スナップショットの Exact 復元など）に委ねる。

フォルダも、他のアセットと同様にこの所有権判定の対象になる。どのルールにもマッチしないフォルダ（`IncludeFolders()` を呼ぶルールが1つも無い場合を含む）は無マッチとして扱われ、`CleanupStaleEntries` が有効なら、所有グループ内のそのフォルダのエントリは作成者が AddressTeller か利用者かを問わず、ファイルのエントリと同様に削除される。

下記（[フォルダは明示的な opt-in を必要とする](#フォルダは明示的な-opt-in-を必要とするincludefolders)参照）に挙げているパスの除外条件の一部は、以前のバージョンから厳格化されている。例えば Config Folder の除外は、以前は実際の配下だけを除外しており、名前が同じ文字列で始まっているだけの隣接フォルダは除外していなかった。`CleanupStaleEntries` が有効な場合、こうした厳格化の後の最初の apply で、新たに無効と判定されるようになったアセットの所有グループ内エントリが削除されることがある。対象となる具体的な範囲とアップデート前の準備については、[CHANGELOG.ja.md](../CHANGELOG.ja.md) の「0.4.x からのアップデート」の注記を参照。

## フォルダは明示的な opt-in を必要とする（IncludeFolders）

`AssetDatabase.GetAllAssetPaths()` はファイルと一緒にフォルダのパスも返す。パスを前方一致で判定するルール（特に `Match.InFolder(...)` は単純な `StartsWith`）は、対策なしではフォルダ配下のファイルと同じ感覚でサブフォルダにもマッチしてしまう。そのようなルールをフォルダに適用すると、Addressables の「フォルダエントリ」が作られ、配下の全アセットを暗黙に含むようになる。これは AddressTeller が同じファイル群に対してすでに作っている個別エントリと二重管理になる。

フォルダを一律で除外する（手動でなら Addressables 自身が許しているフォルダへの意図的なマッチまで封じてしまう）のではなく、ルールごとに `IncludeFolders()` で明示的に opt-in する方式にした。`IncludeFolders()` を呼ばないルールはフォルダを一切見ない（`Where()` が呼ばれない）ため、既存のルールは今まで通りの挙動を保つ。

opt-in したルールであっても、一部のフォルダは対象にならない。Addressables 自身がそもそもエントリ登録を受け付けないパスだからであり、この判定はファイルと同じパス有効性チェックをフォルダにもそのまま適用したもの（詳細は[評価対象から除外されるアセット](writing-rules.ja.md#評価対象から除外されるアセット)を参照）で、実際にファイルかフォルダかを問わずパス文字列だけで判定される。具体的には: `Assets` ルート、名前が `Editor` であるフォルダ自体、`Editor` という名前のフォルダの**配下**にあるフォルダ（これは配下の除外であり、`Editor` フォルダ自身だけの話ではない。例えば `Assets/Game/Editor` が除外される結果、その配下の `Assets/Game/Editor/SubFolder` も除外される）、パッケージ自身のルートフォルダ（`Packages/<pkg>` でそれ以上の階層がないもの）、そして設定済みの Addressables Config Folder 自体とその配下（Addressables 本体と同じ単純な前方一致のため、名前が同じ文字列で始まっているだけの別フォルダ、例えば `Assets/AddressableAssetsData_Backup` も除外される）、が対象になる。なおこの判定はパス文字列のみに基づくため、`Editor` という名前で始まる別のフォルダの直下にある本物の `Editor` フォルダ（例: `Assets/EditorArt/Editor`）は除外されない、という取りこぼしもある。これは Addressables 本体の判定が元々持つ既知の限界であり、AddressTeller は独自に補うのではなく意図的にそれをそのまま踏襲している。

## AddressTeller は既定を制限することはあっても選択肢は奪わない／手動で拒否されるものは AddressTeller でも作らない

AddressTeller のルールは、Unity の Addressables「Groups」ウィンドウで手動でできること（ドラッグ登録、Inspector の Addressable チェックボックス等）と突き合わせて設計されています。

- Groups ウィンドウで手動登録できるものは、AddressTeller のルールからも同じことができる経路を必ず残します。既定で制限すること自体は問題ありません。フォルダが具体例で、既定ではどのルールもフォルダを見ませんが、ルールは `IncludeFolders()`（上記[フォルダは明示的な opt-in を必要とする](#フォルダは明示的な-opt-in-を必要とするincludefolders)参照）で opt-in すれば、Addressables 自身が手動登録を許しているものを対象にできます。
- 逆に、Groups ウィンドウ自身が登録を拒否する対象（例: `Editor` フォルダ自体、`Assets` ルート、`.preset`/`.asmdef`/パッケージ自身の `package.json` などの特殊アセット、`Assets/` またはパッケージ自身のフォルダの外にあるパス、設定済みの Config Folder）は、AddressTeller のルール経由でも同様に拒否されます（[評価対象から除外されるアセット](writing-rules.ja.md#評価対象から除外されるアセット)参照）。自動化によって手動では作れないものが意図せず作られることはありません。

これは既定を安全側の保守的な挙動にすること（上記「[削除は資産単位の所有権で判定する](#削除は資産単位の所有権で判定する)」参照）と両立します——既定で制限すること自体は問題なく、Addressables が手動で許可しているものについては明示的なオプトインの経路が残っていれば十分です。

## 公開APIと内部実装の境界

利用者が触れるべき面を最小に保つため、公開（`public`）にするのは次に限る。それ以外の評価エンジン・Addressables 統合の実装詳細は `internal` とし、将来のリファクタリングで自由に変更できる余地を残す。

公開API（代表例であり、網羅的な一覧ではない）:

- **ルール定義面**: `AddressRuleBase`、`IAddressRuleBuilder`、`IAddressRuleGroupBuilder`、`Match`、`AssetCondition`、`Naming`、`AssetContext`、`AddressRuleEntry`
- **実行エントリ**: `AddressTellerService`、`AddressTellerSettings`
- **スナップショット**: `AddressTellerSnapshotService`、`SnapshotRestoreMode`、`SnapshotDiff`、`AddressTellerSnapshot`、`SnapshotEntry`
- **結果型**: `ValidationResult`、`ValidationStatus`
- **進捗報告**: `IProgressReporter`、`NullProgressReporter`、`EditorProgressReporter`
- **レポート**: `AddressTellerReportWriter`、`ReportFormat`、`BundleDistributionSerializer`、`DistributionFormat` などのレポートDTO群
- **CLI・メニューエントリ**: `AddressTellerMenu`、`AddressTellerSnapshotMenu`、`AddressTellerExplainMenu`、`AddressTellerCliArgs`
- **インポート時自動適用**: `AddressTellerPostprocessor`
- **ルール単体テスト支援**: `RuleInspector`（`AddressTeller.Testing` namespace）— 実際のAddressablesプロジェクトなしにルール構成結果を検査できる

内部実装（`internal`）:

- ルール収集・評価・説明文生成の実装
- Addressables への書き込み実装
- スナップショットのファイル管理・自動退避・レポート組み立て

これらは `AddressTeller.Core` / `AddressTeller.Editor` の2つのエディタアセンブリに分かれており（アセンブリ構成の詳細は[アーキテクチャ](architecture.ja.md)参照）、テストからはそれぞれのアセンブリで宣言した `InternalsVisibleTo` で限定的に参照できるようにしている。利用者から直接参照されない前提のため、内部実装の型・メソッドはシグネチャを保たずに変更できる。
